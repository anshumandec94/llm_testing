# Metric dictionary

This file explains every metric and artifact column produced by `sim.runner.SimulationRunner` and `sim.hpo.run_hpo`.

Three run types produce metrics:

- **Full simulation** (`experiment_profile=full`): the closed-loop experiment with attendance, actions, feedback, and retraining. Metrics are logged **per round** as MLflow time-series steps.
- **`recommender_only`** (`experiment_profile=recommender_only`): a first-batch diagnostic pass over held-out items with no simulated feedback loop.
- **HPO** (run via `sim.hpo.run_hpo`): wraps many `recommender_only` candidate runs and logs summary metrics for the winning config.

---

## Metric naming

Every MLflow metric is namespaced with a `group/` prefix so the MLflow UI groups related metrics together.
The groups are `meta/`, `ranking/`, `sim/`, `popularity/`, `score/`, `correlation/`, `error/`, and `rating/`.

Columns inside the parquet artifacts are **not** namespaced.
Only the MLflow metric keys and the matching `summary.csv` columns carry the prefix.

## Full simulation metrics

Logged per round (MLflow step = round number).

### Attendance and engagement

| Metric | Meaning | How to read it | Example |
| --- | --- | --- | --- |
| `sim/attendance_rate` | Fraction of eval users who attended in that round. | Higher means more users showed up and were eligible to receive recommendations. | `0.72` means 72% of eval users attended. |
| `sim/mean_attention_consumed` | Mean attention budget spent by attending users during the round. | Higher means users spent more of their limited attention budget. | `0.9` means users nearly exhausted one unit of attention on average. |

### Retrieval quality (attending users, first batch only)

| Metric | Meaning | How to read it | Example |
| --- | --- | --- | --- |
| `ranking/hit_rate` | Mean per-user fraction of held-out items recovered by the **first** recommendation batch. | Higher is better. `0` means the first batch never surfaced held-out items. | `0.10` means a user recovered 10% of their held-out set on average. |
| `ranking/ndcg_at_{k}` | Mean ranking quality of the first batch, discounted by rank. Emitted for `k = rec_list_size` and for every `k` in `ndcg_eval_ks`. | Higher is better; hits near the top count more. | `ranking/ndcg_at_6 = 0.35` is much better than `0.05`. |
| `sim/holdout_recall` | Mean fraction of each user's held-out set surfaced **across the whole round**, including re-requests. | Higher means the round exposed more relevant items somewhere in the round. | `0.25` means one quarter of held-out items were surfaced by the end of the round. |

### Feedback

| Metric | Meaning | How to read it | Example |
| --- | --- | --- | --- |
| `sim/mean_signal_strength` | Mean numeric feedback value generated by explicit `rate` actions in that round. | Higher means stronger positive ratings were sent back to the recommender. | `3.8` means ratings averaged 3.8 out of 5. |
| `sim/action_watch_frac` | Fraction of all actions that were `watch`. | The action mix helps explain feedback quality and user behavior. | `0.50` means half of all actions were watches. |
| `sim/action_rate_frac` | Fraction of all actions that were `rate`. | Higher means more explicit ratings were generated. | `0.20` means 20% of actions were ratings. |
| `sim/action_addlist_frac` | Fraction of all actions that were `add_to_list`. | Higher means more medium-strength positive intent without immediate watching. | `0.30` means 30% of actions were add-to-list events. |

## `recommender_only` metrics

### Retrieval and ranking quality

| Metric | Meaning | How to read it | Example |
| --- | --- | --- | --- |
| `meta/user_count` | Number of eval users included in the diagnostic run. | Mostly a coverage / sanity-check metric. | `12834` means diagnostics were computed for 12,834 users. |
| `ranking/hit_rate` | Mean per-user fraction of held-out items hit by the first recommendation batch. | Higher is better. Same interpretation as in the full simulation profile. | `0.02` means 2% of held-out items were recovered on average. |
| `ranking/ndcg_at_{k}` | Mean first-batch ranking quality against held-out items. Emitted for `k = rec_list_size` and for every `k` in `ndcg_eval_ks`. | Higher is better. | `0.11` beats `0.03`. |
| `ranking/frac_users_with_hit` | Fraction of users who got **at least one** held-out hit in the first batch. | Higher is better and easier to interpret than raw hit rate. | `0.18` means 18% of users saw at least one held-out item. |

### Popularity diagnostics

| Metric | Meaning | How to read it | Example |
| --- | --- | --- | --- |
| `popularity/rec_mean` | Mean of each user's average recommendation popularity (training-set interaction count). | Higher means the recommender tends to surface more popular items. | `4000` means the average recommended item had about 4,000 training interactions. |
| `popularity/rec_std` | Mean within-user spread of recommendation popularity. | Higher means the first batch mixes blockbuster and niche items more broadly. | `2500` means popularity within a user's batch varies a lot. |
| `popularity/heldout_mean` | Mean of each user's average held-out-item popularity. | This is the "what the user actually consumed later" popularity baseline. | `16000` means held-out items were much more popular than the recommendations. |
| `popularity/heldout_std` | Mean within-user spread of held-out-item popularity. | Helps show whether held-out behavior itself is narrow or broad in popularity space. | `5000` means users' held-out items vary widely in popularity. |
| `popularity/delta_mean` | Mean of `recommended_popularity_mean − heldout_popularity_mean` across users. | Negative means recommendations are less popular than users' held-out histories; positive means more popular. | `-12000` means recommendations were much less popular than the held-out baseline. |
| `popularity/delta_std` | Cross-user spread of popularity deltas. | Higher means popularity mismatch varies a lot across users. | `8000` means some users get much more niche or much more mainstream lists than others. |
| `popularity/frac_rec_gt_heldout` | Fraction of users whose average recommended popularity exceeded their held-out average popularity. | Above `0.5` means the recommender is more popularity-seeking than users' held-out behavior for most users. | `0.11` means only 11% of users received more popular recommendations than their held-out baseline. |

### Residual-target diagnostics

For these metrics, the held-out target is **debiased first**:

`debiased_rating = observed_rating − (global_bias + user_bias + item_bias)`

This makes the target comparable to latent dot-product scores, which live in residual / affinity space rather than raw 1–5 rating space.

| Metric | Meaning | How to read it | Example |
| --- | --- | --- | --- |
| `rating/heldout_mean` | Mean of each user's average debiased held-out rating. | Near `0` means the held-out set is close to the train-set bias baseline on average. | `0.12` means held-out ratings were slightly above baseline. |
| `rating/heldout_std` | Mean within-user spread of debiased held-out ratings. | Higher means held-out residual preference strength varies more within each user. | `0.48` means held-out residuals span a moderate range. |
| `score/rec_mean` | Mean of the recommender latent residual scores on each user's held-out items. | Higher means the recommender assigns stronger residual affinity to held-out items. | `0.08` means held-out items look mildly attractive in recommender latent space. |
| `score/rec_std` | Mean within-user spread of recommender residual scores over held-out items. | Higher means the recommender distinguishes strongly between a user's held-out items. | `0.30` means some held-out items score much higher than others. |
| `score/int_mean` | Mean of the internal SVD latent scores on each user's held-out items. | Higher means the internal preference model scores held-out items more strongly. | `0.42` means the internal model sees strong affinity in its own latent space. |
| `score/int_std` | Mean within-user spread of internal latent scores over held-out items. | Higher means the internal model sharply separates stronger and weaker held-out items. | `0.15` means internal scores vary, but less than the recommender example above. |
| `score/gap_mean` | Mean of `heldout_recommender_score_mean − heldout_internal_score_mean` across users. | Negative means the internal model tends to score held-out items higher than the recommender; positive means the reverse. | `-0.35` means the internal model is more favorable to held-out items on average. |
| `score/gap_std` | Cross-user spread of score-mean gaps. | Higher means the relative advantage of one model over the other varies across users. | `0.22` means some users favor the recommender while others strongly favor the internal model. |
| `score/frac_rec_gt_int` | Fraction of users for whom the recommender's mean held-out score exceeded the internal model's. | Above `0.5` means the recommender scores held-out items higher in its own latent space for most users. | `0.44` means the internal model wins for most users. |

### Residual error diagnostics

These measure how far each model's latent score sits from the debiased held-out target, rather than how well it correlates with it.
The `error/rec_*` and `error/int_*` families are per-user errors averaged across users, ignoring users whose value is `NaN`.
The `error/global_*` family pools every held-out row into a single error.

`sim.hpo` selects candidates on one of these by default (`error/rec_mse`), so they are the metrics most likely to drive an HPO run.

| Metric | Meaning | How to read it | Example |
| --- | --- | --- | --- |
| `error/rec_mse` | Mean per-user MSE between debiased held-out ratings and recommender residual scores. | Lower is better. This is the default HPO selection metric. | `0.62` beats `0.90`. |
| `error/rec_rmse` | Mean per-user RMSE for the recommender. | Lower is better. Same units as the debiased rating scale. | `0.79` means typical error of about 0.8 rating points. |
| `error/rec_mae` | Mean per-user MAE for the recommender. | Lower is better. Less sensitive to outliers than RMSE. | `0.61` means the median-ish error is about 0.6. |
| `error/int_mse` | Mean per-user MSE for the internal SVD model. | Lower is better. Direct comparator to `error/rec_mse`. | `0.55` means the internal model fits held-out residuals better. |
| `error/int_rmse` | Mean per-user RMSE for the internal model. | Lower is better. | `0.74` beats the recommender example above. |
| `error/int_mae` | Mean per-user MAE for the internal model. | Lower is better. | `0.58` beats the recommender example above. |
| `error/global_rec_rmse` | RMSE across **all** held-out rows for the recommender, ignoring user boundaries. | Lower is better. Weights heavy users more than the per-user average does. | `0.81` is close to the per-user RMSE, so user weighting matters little. |
| `error/global_rec_mae` | MAE across all held-out rows for the recommender. | Lower is better. | `0.63` means typical absolute residual error of 0.63. |
| `error/global_int_rmse` | RMSE across all held-out rows for the internal model. | Lower is better. Direct global comparator to the recommender. | `0.76` means the internal model wins globally too. |
| `error/global_int_mae` | MAE across all held-out rows for the internal model. | Lower is better. | `0.59` means the internal model wins globally too. |

### Residual correlation diagnostics

| Metric | Meaning | How to read it | Example |
| --- | --- | --- | --- |
| `correlation/rec_pearson` | Mean per-user Pearson correlation between debiased held-out ratings and recommender residual scores. | Higher is better if you care about linear agreement in residual space. | `0.18` means modest linear alignment. |
| `correlation/rec_spearman` | Mean per-user Spearman rank correlation between debiased held-out ratings and recommender residual scores. | Higher is better if you care about relative ordering more than exact spacing. | `0.25` means the recommender roughly preserves ranking order in residual space. |
| `correlation/int_pearson` | Mean per-user Pearson correlation between debiased held-out ratings and internal latent scores. | Lets you compare the internal model's residual alignment to the recommender's. | `0.31` means the internal model tracks residual preference better than the previous recommender example. |
| `correlation/int_spearman` | Mean per-user Spearman correlation between debiased held-out ratings and internal latent scores. | Higher means stronger monotonic agreement. | `0.34` means the internal model ranks stronger residual items more consistently. |
| `correlation/global_rec_pearson` | One Pearson correlation computed across **all** held-out rows, ignoring user boundaries. | Useful as an overall signal, but can hide user-level heterogeneity. | `0.09` means weak global linear alignment. |
| `correlation/global_rec_spearman` | One Spearman correlation across all held-out rows for the recommender. | Good for coarse global rank agreement. | `0.14` means weak but positive ordering alignment. |
| `correlation/global_int_pearson` | One Pearson correlation across all held-out rows for the internal model. | Direct global comparator to the recommender value above. | `0.22` means stronger global linear alignment than the recommender example above. |
| `correlation/global_int_spearman` | One Spearman correlation across all held-out rows for the internal model. | Direct global comparator to the recommender rank alignment. | `0.28` means stronger global rank alignment than the recommender example above. |
| `correlation/frac_rec_pearson_gt_int` | Fraction of users for whom the recommender's per-user Pearson residual correlation beat the internal model's. | Above `0.5` means the recommender wins this comparison for most users. | `0.27` means the internal model wins for most users. |

## HPO metrics

These are logged on the parent `hpo-search` MLflow run. Each candidate also logs the full `recommender_only` metric set above on its own nested run.

| Metric | Meaning | How to read it |
| --- | --- | --- |
| `best_validation_{metric_name}` | Value of the selection metric for the winning candidate on the **validation** split. `{metric_name}` is the resolved selection metric, so the key keeps its namespace (e.g. `best_validation_error/rec_mse`). | Direction depends on `minimize_selection_metric`; this is the score that drove the selection. |
| `best_validation_frac_users_with_hit` | Fraction of users with at least one hit for the winning candidate on the validation split. | Higher is better. Useful sanity-check alongside the primary metric. |
| `best_final_{metric_name}` | Value of the selection metric for the winning config re-run on the **held-out** split (e.g. `best_final_error/rec_mse`). | The number you should compare across HPO runs. |
| `best_final_frac_users_with_hit` | Fraction of users with at least one held-out hit for the winning config on the final split. | Companion coverage metric for the final evaluation. |

The `selection_metric` field in `configs/hpo*.json` takes a full namespaced summary column, such as `error/rec_mse` or `ranking/frac_users_with_hit`.
The single shorthand `ndcg_at_k` is also accepted and expands to `ranking/ndcg_at_{rec_list_size}`.

## Artifact files

### `recommender_only` artifacts

#### `diagnostics/recommender_only_user_diagnostics.parquet`

One row per simulated user. All per-user metrics before aggregation.

| Column | Meaning |
| --- | --- |
| `evaluation_split` | Which split was used (`validation` or `held_out`). |
| `userId` | Base user ID from the dataset. |
| `simulation_user_id` | Simulated user ID (equals `userId` in `one_to_one` mode; negative int in `one_per_agent_type` mode). |
| `agent_type` | Agent type assigned to this simulation user. |
| `recommended_item_count` | Number of items in the first recommendation batch. |
| `heldout_item_count` | Number of held-out items for this user. |
| `hit_rate` | Per-user first-batch hit rate. |
| `ndcg_at_{k}` | Per-user NDCG. Present for `rec_list_size` and for every `k` in `ndcg_eval_ks`. |
| `recommended_popularity_mean` | Mean training-set popularity of recommended items. |
| `recommended_popularity_std` | Std of training-set popularity of recommended items. |
| `heldout_popularity_mean` | Mean training-set popularity of held-out items. |
| `heldout_popularity_std` | Std of training-set popularity of held-out items. |
| `popularity_mean_delta` | `recommended_popularity_mean − heldout_popularity_mean`. |
| `heldout_debiased_rating_mean` | Mean debiased held-out rating. |
| `heldout_debiased_rating_std` | Std of debiased held-out ratings. |
| `heldout_recommender_scored_count` | Number of held-out items that had a valid recommender score (non-NaN). |
| `heldout_internal_scored_count` | Number of held-out items that had a valid internal model score (non-NaN). |
| `heldout_recommender_score_mean` | Mean recommender residual score over held-out items. |
| `heldout_recommender_score_std` | Std of recommender residual scores over held-out items. |
| `heldout_internal_score_mean` | Mean internal SVD score over held-out items. |
| `heldout_internal_score_std` | Std of internal SVD scores over held-out items. |
| `heldout_recommender_residual_pearson` | Per-user Pearson corr between debiased ratings and recommender scores. |
| `heldout_recommender_residual_spearman` | Per-user Spearman corr between debiased ratings and recommender scores. |
| `heldout_internal_residual_pearson` | Per-user Pearson corr between debiased ratings and internal scores. |
| `heldout_internal_residual_spearman` | Per-user Spearman corr between debiased ratings and internal scores. |
| `heldout_recommender_mse` | Per-user MSE between debiased ratings and recommender scores. |
| `heldout_recommender_rmse` | Per-user RMSE between debiased ratings and recommender scores. |
| `heldout_recommender_mae` | Per-user MAE between debiased ratings and recommender scores. |
| `heldout_internal_mse` | Per-user MSE between debiased ratings and internal scores. |
| `heldout_internal_rmse` | Per-user RMSE between debiased ratings and internal scores. |
| `heldout_internal_mae` | Per-user MAE between debiased ratings and internal scores. |
| `heldout_score_mean_gap` | `heldout_recommender_score_mean − heldout_internal_score_mean`. |
| `comparison_item_count` | Backward-compat alias for `heldout_item_count`. |
| `comparison_popularity_mean` | Backward-compat alias for `heldout_popularity_mean`. |
| `comparison_popularity_std` | Backward-compat alias for `heldout_popularity_std`. |

#### `recs/recommender_only_recommendations.parquet`

One row per recommended item per user.

| Column | Meaning |
| --- | --- |
| `evaluation_split` | Which split was used (`validation` or `held_out`). |
| `userId` | Base user ID. |
| `simulation_user_id` | Simulated user ID. |
| `agent_type` | Agent type for this user. |
| `rank` | Position of this item in the recommendation list (1 = top). |
| `movieId` | Recommended item ID. |
| `popularity` | Training-set interaction count for this item. |
| `is_held_out_hit` | `1` if this item is in the user's held-out set, `0` otherwise. |

#### `diagnostics/recommender_only_heldout_scores.parquet`

One row per held-out item per user. Used for the residual-correlation metrics.

| Column | Meaning |
| --- | --- |
| `evaluation_split` | Which split was used (`validation` or `held_out`). |
| `userId` | Base user ID. |
| `simulation_user_id` | Simulated user ID. |
| `agent_type` | Agent type for this user. |
| `movieId` | Held-out item ID. |
| `rating` | Raw held-out rating (1–5 scale). |
| `rating_bias` | Train-set bias for this user/item pair: `global_bias + user_bias + item_bias`. |
| `debiased_rating` | `rating − rating_bias`. This is the residual target used for all correlation metrics. |
| `recommender_score` | Recommender latent residual score (`user_factor · item_factor`). `NaN` if the item has no factor. |
| `internal_score` | Internal SVD latent affinity score. `NaN` if the item has no factor. |

### Full simulation artifacts

#### `recs/recs_round_{NNN}.parquet`

One row per candidate item per request per attending user. Written every round.

| Column | Meaning |
| --- | --- |
| `round` | Round number (1-indexed). |
| `request` | Request number within the round (1 = first batch, 2 = re-request, etc.). |
| `userId` | Base user ID. |
| `simulation_user_id` | Simulated user ID. |
| `agent_type` | Agent type for this user. |
| `movieId` | Candidate item ID. |
| `rank` | Position in the agent-ranked list for this request (1 = highest-scored). |
| `is_held_out` | `True` if this item is in the user's held-out set. |
| `interaction` | Action taken (`watch`, `rate`, `add_to_list`) or `None` if ignored. |
| `signal` | Numeric signal for the action, or `None` if ignored. Explicit ratings are on a 1–5 scale; `watch` and `add_to_list` use configured constants but do **not** feed back into model updates. |

#### `recs/recs_round_{NNN}_subgroups.parquet`

Aggregated per-agent-type summary for each round. Useful for comparing agent types within a mixed-population run.

| Column | Meaning |
| --- | --- |
| `agent_type` | Agent type label. |
| `shown_count` | Total number of items shown to users of this agent type in the round. |
| `heldout_hit_count` | Total number of those items that were in a user's held-out set. |
| `round` | Round number. |

---

### Shared artifacts

#### `summary.csv`

One row per round (full simulation) or one row total (recommender_only). Contains all MLflow metrics for the run in a flat CSV — useful for quick analysis without the MLflow UI.
